## 1. 项目问题

小林在一家服装网店下了单，收到两件衬衫，其中一件尺码不合适。她在聊天软件上找客服说"要换 M 码"，客服让她发照片，她发完就去忙了；两天后客服已经忘了这单，仓库却收到了退回的包裹，不知道对应哪次申请，于是把包裹堆在一旁。小林又问了一遍客服，客服重新登记了一次，结果同一个商品出现两条处理记录。

现在的问题是：**一次退换货涉及消费者、客服、仓库三个岗位，各自只掌握一部分信息，靠聊天记录传递状态，导致重复处理、状态不明、无人能对"这单进行到哪一步"给出准确回答。**

系统要帮助的是这三个岗位，以及需要复盘售后情况的店铺负责人：把一次售后从申请到关闭的全过程放进同一张售后单里，每个岗位在自己的工作台看到自己该做的事，每次状态变化都留下记录。

## 2. 使用岗位

| 岗位 | 登录后要完成的事情 |
| --- | --- |
| 消费者 | 查看自己的模拟订单和订单商品；对某个订单商品发起退货或换货申请；按客服要求补充说明和图片凭证；查看售后进度和时间线 |
| 售后客服 | 查看待处理售后单队列；核对申请条件（订单归属、售后期限、申请数量）；要求补充材料；同意退回并给出退回指引；拒绝并说明理由；根据验货结果最终确认换货、模拟退款或拒绝 |
| 仓库人员 | 查看客服已同意退回、等待收货的售后单；登记收到退回包裹；记录验货结果（合格/异常）与问题说明；换货时登记模拟补发单号 |

三类岗位使用不同账号登录，看到的页面和可执行的操作不同。

## 3. 完整流程

### 3.1 正常流程（以换货为例）

1. **消费者发起**：消费者在自己的已完成订单中选择一件订单商品，选择售后类型为"换货"，填写数量、原因（尺码不合适）和说明，上传一张商品照片，提交。售后单产生，状态为**待审核**。
2. **客服审核**：客服在工作台看到这条待审核售后单，检查订单归属、是否在售后期限内、申请数量是否超过可售后数量。判断符合条件，点击"同意退回"，填写退回地址指引和联系人说明。状态变为**待消费者退回**。
3. **消费者寄回**：消费者在线下寄出包裹（系统不接快递接口），回到页面确认"已寄出"，填写自己记录的包裹单号。状态变为**待收货**。
4. **仓库收货验货**：仓库人员在工作台看到这条待收货售后单，登记实际收到的包裹，检查商品（吊牌完整、未洗涤、无破损），记录验货结果为"合格"。状态变为**待客服最终确认**。
5. **客服最终确认**：客服根据验货结论，确认换货成立，登记模拟补发单号（换货）或记录模拟退款结果（退货）。状态变为**已完成**，售后单关闭。
6. 全过程每一步都在售后时间线上留下岗位、时间、动作和说明。

### 3.2 异常流程一：客服要求补充材料

消费者提交的说明过于笼统（只写"有问题"，没有照片）。客服点"要求补充"，填写缺什么材料。状态变为**待补充**。消费者在工作台看到要求，补充说明和照片后重新提交，售后单回到**待审核**，之前的沟通记录保留。

### 3.3 异常流程二：仓库验货不合格

仓库收到包裹发现衬衫已经洗涤过，不具备换货条件，登记验货结果为"异常"并填写具体现象。状态变为**待客服最终确认**（不是自动拒绝）。客服查看验货记录后自行决定：拒绝本次售后（填写理由，状态**已拒绝**并关闭），或考虑特殊情况继续处理（在时间线上写明结论）。系统不判断真实商品质量责任。

### 3.4 异常流程三：申请被直接拒绝

客服检查发现该订单不在本人账号下，或该商品已有一次处于处理中的售后单，客服点"拒绝"并填写理由，状态变为**已拒绝**，消费者可在时间线上看到理由。

## 4. 关键规则

### 4.1 必须满足的条件

- 只能对**本人**状态为"已完成"的模拟订单中的订单商品申请售后；
- 申请数量 ≤ 该订单商品的**可售后数量**（订单数量 − 已关闭售后单占用数量）；
- 同一订单商品不允许存在两条**未关闭**的售后单；
- 退货和换货两种类型都必须填写申请原因和文字说明；
- 换货完成后必须记录模拟补发单号；退货完成后必须记录模拟退款结果（金额由系统按商品单价 × 数量算出，不涉及真实资金）。

### 4.2 不允许发生的操作（状态跳转约束）

| 不允许 | 原因 |
| --- | --- |
| 消费者跳过客服审核，直接把售后单标记为"可以退回" | 是否符合售后条件由客服判断 |
| 仓库在未收到"客服同意退回"的售后单时登记收货和验货 | 会产生无法对应申请的孤儿包裹，正是要解决的问题 |
| 仓库验货后直接把售后单置为已完成或已拒绝 | 验货只是事实登记，退款/换货结论由客服作出 |
| 客服在还没有验货记录时直接确认换货或退款 | 系统必须先有仓库的收货与验货结论 |
| 任何岗位把已关闭（已完成/已拒绝）的售后单重新打开并覆盖原记录 | 需要重新处理时应新建售后单，保留历史 |
| 拒绝、要求补充材料、验货异常时不填原因就提交 | 无理由的结论无法追溯 |

### 4.3 各岗位可查看与可处理的范围

| 岗位 | 可查看 | 可处理 |
| --- | --- | --- |
| 消费者 | 仅本人的订单、本人发起的售后单及其时间线 | 发起申请、补充材料、确认已寄回 |
| 售后客服 | 全部售后单与订单 | 审核、要求补充、同意退回、拒绝、最终确认换货/退款 |
| 仓库人员 | 全部处于"待收货""待验货"的售后单及其收货记录 | 登记收货、登记验货结果与问题、登记补发单号 |

普通消费者**不能**查看他人订单和售后资料；客服不能填写验货结果，仓库不能填写最终退款结论。

### 4.4 留痕要求

每一次状态变化都记录：动作名称、变更前状态、变更后状态、操作账号、操作岗位、时间、文字说明。时间线按售后单聚合展示，消费者看到对外说明，客服和仓库看到完整内部记录。

## 5. 第一版范围

### 5.1 必须完成

1. 模拟订单数据：账号、订单、订单商品（名称、颜色、尺码、数量、单价、下单与完成时间）；
2. 退货、换货两种售后类型；
3. 售后申请：原因分类、申请数量、文字说明、图片凭证上传（支持多张）；
4. 客服审核动作：要求补充材料、同意退回并给出退回指引、拒绝（必填理由）；
5. 仓库收货登记与验货结果（合格 / 异常 + 问题说明）；
6. 换货场景记录模拟补发单号；
7. 退货场景记录模拟退款结果与金额，不接真实资金；
8. 售后单时间线；
9. 三个岗位各自的工作台（列表 + 待办数量）与售后单详情页；
10. 按状态、售后类型、申请时间查询售后单；
11. 登录与角色权限、数据归属校验；
12. 数据库建表脚本、初始化虚构数据、演示账号。

### 5.2 明确不做

- 商品浏览、搜索、购物车、真实下单与支付；
- 接入真实电商平台、真实快递轨迹、真实退款接口；
- 判断真实商品质量责任或责任归属结论；
- 复杂优惠分摊、跨境税费、多仓退货、部分退款拆分；
- 售后以外的库存管理、采购、财务对账；
- 把大模型作为业务流程的必要环节（常规赛道不要求）。

范围判断依据：1 条主链路（申请 → 审核 → 退回 → 收货验货 → 最终确认 → 关闭）完整跑通，3 类角色，约 6 个核心业务对象，8 个业务状态，6 至 9 个主要页面区域。

## 6. 需求验收示例

**示例 1（正常）**：消费者小林账号下有一笔已完成订单，包含 2 件衬衫。她对其中 1 件发起换货申请，填写数量 1、原因"尺码不合适"、说明并上传 1 张照片，提交后应得到：售后单状态"待审核"，她的工作台能看到这条申请，客服工作台待审核数量 +1。

**示例 2（边界）**：同一订单商品已有一张处于"待审核"的售后单，消费者再次对同一商品提交申请，系统应拒绝并提示该商品已有正在处理的售后；另一例是把申请数量填为 3（订单只有 2 件），系统应拒绝并提示超出可售后数量。

**示例 3（异常）**：客服对一张说明不清的申请点"要求补充材料"并写明缺少照片，售后单状态变为"待补充"；消费者补充照片后重新提交，状态回到"待审核"，且时间线上能看到两次记录。

**示例 4（权限 + 状态约束）**：一张刚提交、还处于"待审核"的售后单，仓库人员尝试登记收货，系统应拒绝并提示需要先由客服同意退回；只有客服点了"同意退回"且消费者确认已寄出后，仓库才能登记。

**示例 5（异常 + 职责边界）**：仓库对某售后单登记验货结果为"异常"，说明"商品已洗涤"。售后单应进入"待客服最终确认"而不是自动关闭；客服可拒绝该申请并填写理由，最终状态"已拒绝"，时间线显示验货记录和拒绝结论两条记录。

**示例 6（越权）**：消费者张三登录后访问 URL 中带有他人售后单编号的详情页，系统应返回无权限提示，不显示该售后单任何内容；张三的订单列表里也查不到这条记录。

### 7.2 待确认问题

1. 课程是否统一提供登录、角色权限、统一响应、文件上传和部署模板？若提供，本项目不自建同类基础设施。
2. 数据库产品和框架版本以课程统一规定为准，本机已确认可用环境为 MySQL 8.0.46 + JDK 17 + Maven 3.9.16，是否接受？
3. 售后期限的天数（示例用"下单后 7 天内"）是否需要按教师提供的行业情境包修改？
4. 图片凭证是否要求真实文件上传与存储大小限制，还是允许先用本地目录存储？
5. 是否需要"店铺负责人"作为第四类角色（争议处理、售后数据统计）？当前按题目要求只做三类角色，负责人视角归入客服。
