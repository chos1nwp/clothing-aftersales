## 3. 四个真实失误与它们各自换来的检查动作

| 失误 | 只有什么动作才能暴露它 | 沉淀下来的固定动作 |
| --- | --- | --- |
| D-06 服务端替调用方做隐式默认过滤（仓库「全部」页签比子页签少） | 浏览器点页面、比较两个页签的条数——接口各自都"对"，合起来不成立 | 缺省语义只允许出现在页面层；服务端不代替调用方默认过滤 |
| D-09 越界改配置，删掉不相干的键又补回成重复键（运行行为没变，所以没有任何测试报错） | 事后 `git show <commit> -- <file>` 逐行看 diff | 提交里出现删除行就问一句「这行属于本次任务吗」；新增键前先 `grep` 同名键 |
| D-12 / D-13 不存在的地址被判 500、文档接口名和代码不一致 | **照着文档手动 `curl` 一遍**。机器跑的路径不会错，只有人读的文档会错 | 文档里每个接口路径/表名/字段名逐个对代码或数据库核；错误码要有归属（400/401/403/404/409/500 各有样本） |
| D-14 并发用例把空响应用 bash 算术蒙成「409+0」通过 | **换环境重跑**（新目录 + `java -jar` 而不是 `spring-boot:run`），时序一变就现形 | 跨进程取证的断言，「读到没有」和「读到的对不对」必须写成两条断言；修脚本的方向是加更严的前置，不是放宽 |

四条合起来是本项目最值钱的经验：**每一类检查都只能抓到它那一类问题**。只跑脚本会漏文档错误，只看页面会漏接口不诚实，只在原目录跑会漏时序缺陷。

## 4. 如果重做一遍，我会改的六个决定

1. **验收脚本先于页面**。本项目脚本是第六至八章才建的，前四章靠手工点击，五个缺陷（D-01/D-02/D-05/D-06/D-08）本来可以在写下第一条断言时就被拦住。
2. **状态机要有一层秒级单测**。89 项断言跑一轮要重灌数据 + 打几十次接口，而「哪个状态允许哪个动作」本质是纯函数，JUnit 表驱动几十毫秒就覆盖完了；现在的代价是改一行流转要跑整套脚本。
3. **岗位视图与接口过滤一开始就分层**。D-06 的根因是同一条岗位约束被实现了两次（页面一次、接口一次），第二次还是隐式的。设计文档里应写死「接口只认参数」。
4. **错误码归属当作设计产物**。404 处理缺失（D-12）不是实现漏写，是设计时只列了业务码没列传输层码；第三章接口清单里应有一列「客户端可能踩到的错误码」。
5. **部署文档第四章就开工**。第九章第一次在新目录执行 `mvn package` 就撞上打包插件离线不可用，这种"环境类事实"越晚发现越贵。
6. **若走挑战赛道，需要补的是 AI 输出质量那一层**。本项目只做到了"AI 产物必须有人核对的锚点"，还没有样例集（明确/模糊/冲突/依据不足四类）与打分口径，这是下一步而不是已完成。

### 预期提问与答法

- **为什么不用 Spring Security？** 课程要求小型系统讲清权限口径；Session + `@RequireRole` 拦截器够用且只有几十行。代价已登记：无 CSRF、无密码策略，生产要换过滤器链。
- **退款金额为什么是模拟的？** 题目不接真实资金，重点是"金额从哪来、能不能追溯"。服务端按单价×数量算，前端传什么都不生效（用例 F2/F3）。
- **没有 JUnit 怎么保证不回归？** 事实上的回归入口是 89 项端到端断言 + 数据库对账，改任何流转跑它；我在 §4 已承认状态机缺秒级单测，这是明确的后续项。
- **并发怎么保证只有一个成功？** `update … where id=? and status=?`，影响 0 行即 409；状态本身就是版本条件。两个客服账号真并发跑过，动作日志只有 1 条（E1–E4）。
- **数据怎么在新环境重现？** 三个 SQL 脚本 + 相对 `NOW()` 的演示日期，`sql/data.sql` 可任意时刻重放；三个脚本每次开头就重放它。
