# AI 全栈课程贯穿式大作业选题方案

> 适用时间：第一章结束后选题，后续章节持续建设，课程结束时完成验收  
> 赛道设置：常规赛道4题，挑战赛道2题  
> 适用对象：具备少量编程基础、尚未完整开发过Web业务系统的学生

## 一、大作业定位

大作业不是课程结束前临时完成的综合练习，而是贯穿整门课程的一条实践主线。

在第一章结束后选择一个行业方向。此时只需要看懂业务背景、主要角色和大致流程，不要求立即写需求文档或设计数据库。后续每学习一章，就为同一个项目补充一层成果：

~~~mermaid
flowchart LR
    A[第一章：理解行业并选择方向] --> B[需求：确认角色、问题与边界]
    B --> C[设计：页面、数据与接口]
    C --> D[编码：完成核心业务闭环]
    D --> E[AI协作与版本管理]
    E --> F[联调、Review与测试]
    F --> G[部署、演示与交付]
~~~

本方案强调的是“企业怎样使用系统完成工作”，不是模仿一个看起来像企业官网的页面。每个选题都必须接触以下内容：

- 不同岗位的人分别负责什么；
- 一项业务从哪里发起，经过哪些人，最后怎样结束；
- 企业用什么单据或记录传递信息；
- 正常流程之外会出现什么异常；
- 哪些操作只有特定角色可以执行；
- 系统怎样留下可查询、可追溯的业务记录。

## 二、统一项目边界

### 共同技术路线

所有项目采用课程统一的Web技术路线：浏览器前端、Java后端、MyBatis数据访问和关系数据库。具体框架版本、数据库产品和部署方式由课程统一确定。

教师可以提供登录、角色权限、统一响应、文件上传、日志记录和部署模板。不同小组重点完成不同的业务对象、业务规则和页面流程，不要求重复搭建相同的基础设施。

### 建议规模

- 2至3类核心角色；
- 4至7个核心业务对象；
- 1条必须完整跑通的主业务链路；
- 6至10个主要页面或页面区域；
- 5至8个清楚、有限的业务状态；
- 核心闭环完成后，最多增加1项扩展功能。

### 企业业务系统的共同交付底线

无论选择哪个方向，最终项目至少具备：

- 不同岗位使用不同账号登录；
- 角色权限和业务数据归属有效；
- 一条从发起、受理、处理到结束的业务链路；
- 清楚的状态变化和不允许发生的状态跳转；
- 列表、详情、创建、处理和历史查询；
- 页面、后端接口和数据库真实连接；
- 加载、空数据、成功、失败、冲突和无权限反馈；
- 关键操作留下时间、操作人和处理说明；
- 数据库建表、初始化数据和演示账号；
- Git版本记录、README、测试结果和部署说明；
- 能够在新目录或新环境重新运行并完成核心演示。

### 行业接触方式

可以不进入企业生产系统，也不能索取企业隐私数据。需求依据可以来自：

1. 教师提供的行业情境包、岗位说明和脱敏业务样例；
2. 企业官网、帮助中心、公开服务规则和公开表单；
3. 经对方同意的从业者访谈或岗位观察；
4. 对同类软件公开功能和流程的比较。

需要区分“已经确认的行业事实”“根据资料作出的推测”和“仍需验证的问题”。不得把AI生成内容写成企业调研结论。

# 第一部分：常规赛道

常规赛道重点考查小型Web业务系统的完整交付。AI可以参与需求整理、方案比较、编码、Review和测试，但不强制把大模型能力集成到最终产品中。

## 选题一：广告制作公司宣传物料订单管理系统

### 先看这个场景

一家奶茶店准备开业，请广告制作公司在周五前完成两张宣传海报、一块门店展架和一组公众号配图。

客户经理通过聊天软件接到需求，设计人员只看到一句“做得年轻一点”，制作人员又不知道最终尺寸。设计稿修改了两次，大家却说不清客户确认的是哪一版。到了周五，海报做好了，展架还没有完成，客户经理只能逐个人询问进度。

要做的系统，就是把这一笔宣传物料订单从登记、分派、设计、修改到交付的过程管理起来。

### 这是什么项目

广告制作公司为其他企业制作海报、展架、菜单、宣传册和线上配图。系统帮助客户经理登记客户需要什么，帮助设计制作人员看清任务和截止时间，并保留每次修改与最终交付记录。

项目不是建设完整的广告公司ERP，只完成“一笔宣传物料订单怎样按要求交付”。

### 主要使用者

| 角色 | 主要任务 |
| --- | --- |
| 客户经理 | 登记客户、物料要求和截止时间，记录客户确认结果 |
| 业务负责人 | 确认订单范围、分派人员并检查延期情况 |
| 设计制作人员 | 接收海报、展架等任务，上传设计稿并根据意见修改 |

### 核心业务链路

~~~text
客户经理登记宣传物料订单
→ 负责人确认物料清单和截止时间
→ 把海报、展架等任务分派给设计制作人员
→ 设计制作人员上传初稿
→ 客户经理记录客户修改意见
→ 设计制作人员提交新版本
→ 客户经理记录客户确认并完成交付
~~~

### 首版必须完成

- 客户和宣传物料订单基本信息；
- 海报、展架、菜单、宣传册、线上配图等物料任务；
- 每项物料的尺寸、数量、用途、参考说明和截止时间；
- 订单和任务的状态流转；
- 负责人分派设计制作人员；
- 设计稿或成品文件的版本记录；
- 客户修改意见和再次提交记录；
- 按客户、设计人员、截止时间和状态查询订单；
- 订单和物料任务的操作历史。

### 关键业务规则

- 物料清单和截止时间确认后，不能直接覆盖原要求；
- 新增物料或改变截止时间时必须留下变更记录；
- 设计制作人员只能处理分派给自己的物料任务；
- 上传设计稿不等于客户已经确认；
- 新版本不能覆盖旧版本，必须能够查看修改过程；
- 只有客户经理可以记录客户确认结果；
- 订单内所有物料都确认后，整笔订单才能完成。

### 首版不做

- 不接入真实合同、报价、支付和发票；
- 不在线编辑图片，不替代Photoshop等设计软件；
- 不实现印刷设备、材料库存和配送管理；
- 不向真实客户发送邮件或短信；
- 不判断图片版权和广告内容合规性。

### 核心验收场景

1. 客户经理创建包含海报和展架的订单后，负责人能够分别分派任务；
2. 设计人员只能处理分派给自己的物料任务；
3. 初稿上传后进入待客户确认，不能直接标记完成；
4. 客户提出修改意见后，设计人员能够提交新版本，旧版本仍可查看；
5. 海报已确认而展架未完成时，整笔订单仍显示制作中；
6. 已确认订单新增物料或更改日期时留下变更记录；
7. 无权限用户修改订单或他人任务时被拒绝。

### 能够获得的行业认识

从一笔看得见的广告订单出发，理解客户要求怎样变成企业内部任务，也能看见“上传了文件”“客户确认了文件”和“整笔订单完成”为什么是三件不同的事。

## 选题二：服装网店退换货处理系统

### 先看这个场景

小林在一家服装网店买了两件衬衫，收到后发现其中一件尺码不合适，于是申请换货。客服需要确认这件商品是否仍在售后期限内，仓库收到退回包裹后要检查商品，最后再安排补发。

要做的系统，就是让消费者、客服和仓库共同处理这一次换货，并且每个人都知道现在进行到哪一步。

### 这是什么项目

系统模拟一家服装网店的售后部门，处理消费者从申请退货或换货，到仓库验收和售后结束的完整流程。

### 业务背景

电商订单完成后，消费者可能因为错发、破损、尺码不合适或商品质量问题申请售后。客服需要检查订单和售后期限，仓库需要确认退回商品，负责人还要处理争议和异常申请。不同岗位掌握的信息不同，如果只用聊天记录沟通，容易发生重复处理和状态混乱。

项目重点是售后协作，不要求建设完整商城。

### 主要使用者

| 角色 | 主要任务 |
| --- | --- |
| 消费者 | 查看模拟订单、提交售后申请、补充凭证、查看进度 |
| 售后客服 | 审核申请、要求补充材料、同意或拒绝、处理争议 |
| 仓库人员 | 登记退回商品、检查结果和重新发货信息 |

### 核心业务链路

~~~text
消费者选择订单商品并申请售后
→ 客服检查申请条件
→ 消费者补充材料或获得退回指引
→ 仓库登记收货与验货结果
→ 客服确认换货、模拟退款或拒绝
→ 售后单关闭
~~~

### 首版必须完成

- 模拟订单和订单商品数据；
- 退货、换货两种售后类型；
- 申请原因、数量、说明和图片凭证；
- 客服审核、退回补充、同意和拒绝；
- 仓库收货、验货和问题登记；
- 换货时记录模拟补发单号；
- 模拟退款结果记录，不接真实资金；
- 售后时间线和各角色工作台。

### 关键业务规则

- 只能对本人已完成的模拟订单申请售后；
- 申请数量不能超过该订单商品的可售后数量；
- 客服同意退回后，仓库才能登记收货和验货；
- 仓库验货不直接等于退款或换货完成；
- 拒绝、补充材料和验货异常必须填写原因；
- 每次状态变化都保留操作岗位、时间和说明。

### 首版不做

- 不开发商品浏览、购物车和真实下单支付；
- 不接入真实电商平台、快递和退款接口；
- 不判断真实商品质量责任；
- 不实现复杂优惠分摊、跨境税费和多仓退货。

### 核心验收场景

1. 消费者能够对自己的模拟订单商品发起退货或换货；
2. 超过可申请数量或重复申请时系统拒绝；
3. 客服可以要求补充材料，消费者补充后再次进入审核；
4. 未经客服同意，仓库不能提前登记退回商品；
5. 仓库验货异常后，客服能够继续处理并留下结论；
6. 普通消费者不能查看他人订单和售后资料。

### 能够获得的行业认识

理解电商售后是消费者、客服、仓库共同完成的流程，“收到退货”“同意退款”和“售后结束”是不同业务事实。

## 选题三：快递公司异常件处理系统

### 先看这个场景

一件从杭州寄往武汉的包裹，物流信息连续三天没有更新。寄件企业向客服询问，客服创建异常工单并交给武汉站点核实。站点发现包裹标签破损，需要重新确认地址，客服随后把处理进展告诉客户。

要做的系统，不是显示全国所有快递，而是处理这一件“没有正常到达”的包裹。

### 这是什么项目

系统帮助快递公司的客服和站点人员处理延误、破损、地址异常和签收争议，让企业客户能够查询处理进度。

### 业务背景

正常物流轨迹可以由节点扫描不断更新，但真正消耗企业协作成本的往往是异常件。客服收到客户询问后，需要联系站点或运输人员核实情况；运营人员需要分派责任人、限定处理时间，并向客户说明结果。

项目不模拟全国物流网络，而是聚焦“一票货物出现异常后怎样被处理”。

### 主要使用者

| 角色 | 主要任务 |
| --- | --- |
| 企业客户或寄件方 | 查询运单、提交异常反馈、确认处理结果 |
| 客服人员 | 创建异常工单、联系内部岗位、回复客户 |
| 运营或站点人员 | 核实异常、记录处理措施、提交处理结果 |

### 核心业务链路

~~~text
模拟运单产生物流轨迹
→ 客户发现异常
→ 客服创建异常工单
→ 运营人员受理并核实
→ 提交处理方案和结果
→ 客服反馈客户
→ 客户确认或申请继续处理
~~~

### 首版必须完成

- 模拟运单、运输节点和轨迹记录；
- 延误、物品破损、订单标签破损、联系人异常和签收争议四类异常；
- 客户提交异常反馈；
- 客服创建、分类和分派异常工单；
- 运营人员记录核实过程与处理结果；
- 处理时限、即将超时和已经超时标记；
- 客户查看公开进度并确认结果；
- 内部处理记录与客户可见说明分开保存。

### 关键业务规则

- 运单不存在或不属于当前客户时，不显示详细信息；
- 一个未关闭异常可以关联多次沟通，但不能被重复关闭；
- 只有被分派人员可以提交内部处理结果；
- 内部备注不得直接展示给客户；
- 运营提交结果后，由客服确认对外说明；
- 客户不认可处理结果时，工单重新进入待处理并保留原记录。

### 首版不做

- 不接入真实快递公司接口、地图和定位设备；
- 不实现路径规划、车辆调度和全国网点管理；
- 不处理真实理赔、保价和资金结算；
- 不自动认定事故责任。

### 核心验收场景

1. 客户能够查询自己的模拟运单并提交异常反馈；
2. 客服创建工单后，指定运营人员能够受理；
3. 超过处理期限的工单出现明确提示；
4. 内部备注不会出现在客户页面；
5. 运营提交结果后，由客服生成对外反馈；
6. 客户不认可结果时可以重新打开，全部处理过程可追溯。

### 能够获得的行业认识

理解物流系统不仅展示“包裹到哪里了”，还要处理跨岗位协作、内外信息差异、处理时限和责任留痕。

## 选题四：养老院每日照护记录系统

### 先看这个场景

养老院每天早上要协助多位长者用餐、整理房间并参加活动。护理员小周临时被调去处理其他事情，其中一项陪伴任务没有按时完成。管理人员需要及时看到遗漏、重新安排人员，并向家属提供适当的服务记录。

要做的系统，就是让“今天谁需要什么照护、由谁完成、出现问题后怎样处理”变得清楚。

### 这是什么项目

系统帮助养老院记录日常非医疗照护任务，让护理员、管理人员和家属看到清楚、适度且有权限边界的服务信息。

### 业务背景

养老机构每天需要完成用餐协助、活动陪伴、房间整理、物品代办和家属沟通等非医疗服务。纸质记录容易分散，管理人员难以及时发现遗漏，家属也可能因为不了解日常情况而反复询问。

项目只处理课程能够安全模拟的非医疗照护流程，不提供诊断、用药和紧急救治建议。

### 主要使用者

| 角色 | 主要任务 |
| --- | --- |
| 护理员 | 查看当日任务、记录执行情况、上报异常 |
| 机构管理人员 | 制定照护计划、分派任务、检查遗漏和处理异常 |
| 家属 | 查看被授权长者的公开服务记录、提交服务反馈 |

### 核心业务链路

~~~text
管理人员为长者建立非医疗照护计划
→ 系统生成每日任务
→ 护理员执行并记录结果
→ 异常任务提交管理人员处理
→ 管理人员确认可公开摘要
→ 家属查看并反馈
~~~

### 首版必须完成

- 使用虚构姓名和信息的长者档案；
- 非医疗照护项目和计划；
- 根据计划生成当日任务；
- 护理员工作台和任务执行记录；
- 未完成、异常和需要跟进的说明；
- 管理人员检查遗漏并处理异常；
- 区分内部记录和家属可见摘要；
- 家属只能查看被授权长者的信息并提交反馈。

### 关键业务规则

- 护理员只能处理分派给自己的任务；
- 未完成任务不能伪装成已完成，必须选择原因；
- 涉及身体不适、跌倒等情况时，只记录“已上报”和线下处理状态，不给出医疗判断；
- 内部工作记录默认不直接展示给家属；
- 家属账号只能查看绑定长者的公开信息；
- 历史照护记录不能被普通护理员删除或覆盖。

### 首版不做

- 不保存真实身份证、病历、药物和生命体征数据；
- 不提供疾病诊断、用药提醒和紧急处置建议；
- 不接入摄像头、可穿戴设备和门禁；
- 不实现护理费用结算和政府监管上报。

### 核心验收场景

1. 管理人员建立周期计划后能够生成当日任务；
2. 护理员只能完成分派给自己的任务；
3. 任务未完成或出现异常时必须说明原因并进入跟进；
4. 管理人员确认后，家属能够看到适当的服务摘要；
5. 家属不能看到内部备注和其他长者信息；
6. 历史任务、异常处理和家属反馈能够追溯。

### 能够获得的行业认识

理解养老数字化不是简单地“记录老人信息”，而是围绕服务责任、隐私保护、异常上报和家属沟通建立可信流程。

## 常规赛道对比

| 选题 | 主要行业 | 核心业务对象 | 核心能力 | 综合难度 |
| --- | --- | --- | --- | --- |
| 广告物料订单管理 | 企业服务 | 客户、物料订单、设计版本、修改意见 | 分派、改稿、客户确认 | 中 |
| 服装网店退换货 | 电商 | 订单商品、售后单、验货记录 | 数量约束、跨岗位流转 | 中偏高 |
| 快递异常件处理 | 物流 | 运单、轨迹、异常工单、处理记录 | 时限、内外信息隔离 | 中偏高 |
| 养老院每日照护 | 养老服务 | 长者、照护计划、任务、异常 | 周期任务、隐私、授权 | 中 |

# 第二部分：挑战赛道

挑战赛道仍然必须先完成一个可用的Web业务系统，但AI不是完成以后临时加上的聊天框，而是业务流程中的一个必要步骤。

本课程所说的“简单AI原生”包含四个特征：

1. 系统接收用户写下的题目、反馈或说明等自然语言内容；
2. AI把这些内容变成分类、摘要、讲评或需求草稿等结构化候选结果；
3. 用户能够查看AI依据的原始内容，并对结果进行确认和修改；
4. AI失败时业务仍能由人工继续完成。

## 挑战选题一：初中数学作业讲评与错题跟踪助手

### 先看这个场景

初二数学老师批改完45名学生的一次作业，发现很多人都做错了第五题，但错误原因并不完全相同。老师需要统计哪些知识点没有掌握，准备讲评内容，再查看学生订正后是否仍然出错。

要做的系统，是让AI根据原题、标准答案和教师批改结果生成讲评草稿，再由教师确认后发给学生。

### 这是什么项目

系统帮助初中数学教师整理作业结果、生成有依据的讲评草稿和后续练习建议，但不替教师修改分数或给学生下结论。

### 业务背景

K12教师完成一次作业批改后，需要统计共性错误、准备讲评内容，并为不同学生安排后续练习。数据可能分散在表格、纸质记录和教师个人笔记中。生成式AI可以协助归纳和起草，但如果没有题目、标准答案和评分依据，就可能给出错误讲解。

项目聚焦“教师已经批改之后怎样组织讲评和跟踪改进”，不建设完整网校，也不让AI自动决定成绩。

### 主要使用者

| 角色 | 主要任务 |
| --- | --- |
| 教师 | 维护作业、录入批改结果、确认讲评、布置后续练习 |
| 学生 | 查看自己的错题讲解、完成订正并提交疑问 |
| 教研负责人 | 维护知识点和审核公共讲评模板 |

### 核心业务链路

~~~text
教师创建作业并关联知识点
→ 导入虚构的学生答题与人工批改结果
→ 系统统计错误分布
→ AI依据题目和标准答案生成讲评草稿
→ 教师审核、修改并发布
→ 学生订正和反馈
→ 教师查看改进情况
~~~

### 首版必须完成

- 班级、虚构学生、知识点和作业管理；
- 题目、标准答案、评分说明和人工批改结果；
- 按题目和知识点统计错误情况；
- AI生成讲评草稿和候选练习建议；
- 每段讲评关联原题、标准答案；
- 学生查看本人讲评、提交订正和疑问；
- 教师查看订正完成情况。

### AI业务约束

- 没有标准答案或教师依据时，不生成确定性讲解；
- AI输出必须先由教师审核，不能直接发布给学生；
- 模型不可用时，教师仍可手工编写讲评并完成业务流程。

### 首版不做

- 不接入真实学校教务系统和未成年人个人数据；
- 不做人脸识别、课堂监控和行为评分；
- 不让AI自动评分主观题或决定升学结果；
- 不建设直播、题库商城和完整在线考试平台。

### 核心验收场景

1. 教师导入批改结果后，系统能形成正确的错误分布；
2. AI讲评能够关联题目、标准答案和知识点依据；
3. 缺少依据的题目被标记为待教师处理，而不是编造讲解；
4. 未经教师确认的草稿不会展示给学生；
5. 学生只能查看自己的成绩、讲评和订正记录；
6. 教师修改并发布后，学生能够订正并提交疑问；
7. 模型调用失败时，教师仍能手工完成讲评发布。

### 挑战点

不仅要完成教学业务系统，还要区分原始作业数据、统计结果、AI草稿和教师正式结论，并处理未成年人隐私与教师责任边界。

## 挑战选题二：企业报销软件用户反馈与功能改进助手

### 先看这个场景

一家开发企业报销软件的科技公司，一周收到了60条用户反馈。有用户说“上传发票总是失败”，有人说“找不到报销单退回原因”，还有人只是写了一句“审批太麻烦”。产品经理需要逐条阅读、合并相似问题，再决定哪些问题值得进入产品改进计划。

要做的系统，让AI先把反馈按功能和问题类型整理成候选问题卡片，再由产品经理确认，并转成可以交给开发人员的改进任务。

### 这是什么项目

系统帮助报销软件产品团队整理零散的用户反馈。AI负责提取问题、合并相似反馈和起草需求，产品经理负责确认问题是否成立以及是否进入开发。

### 业务背景

企业软件的用户反馈可能来自客服工单、使用调查和客户沟通记录。同一个问题会被不同用户用不同方式表达，一条反馈中也可能同时包含多个问题。如果产品经理只关注声音最大或表达最激烈的用户，就可能错过真正影响使用的问题。

这个项目不自动决定产品该做什么，而是让AI完成第一轮整理，使产品经理能够从原始反馈回查依据、确认问题并建立改进任务。

### 主要使用者

| 角色 | 主要任务 |
| --- | --- |
| 客服人员 | 录入脱敏反馈、补充客户所用功能和处理情况 |
| 产品经理 | 查看AI候选问题、确认或合并问题、建立功能改进任务 |
| 开发或测试人员 | 接收改进任务、更新进度并记录验证结果 |

### 核心业务链路

~~~text
客服录入或导入脱敏用户反馈
→ AI提取涉及功能、问题现象和用户诉求
→ AI把相似反馈组成候选问题卡片
→ 产品经理查看原文并确认、修改或驳回
→ AI为已确认问题生成需求草稿和验收条件
→ 产品经理修改后建立改进任务
→ 开发或测试人员记录实现与验证结果
~~~

### 首版必须完成

- 单条录入和批量导入脱敏反馈；
- 反馈分类包括报销单填写、发票上传、审批进度和退回修改等；
- AI生成候选问题卡片并关联原始反馈；
- 产品经理确认、修改、合并和驳回候选问题；
- AI为已确认问题生成需求说明和验收条件草稿；
- 产品经理修改草稿并建立改进任务；
- 开发或测试人员更新待开发、开发中、待验证和已完成等状态；
- 记录从原始反馈到改进任务和验证结果的完整时间线。

### AI业务约束

- AI只能处理系统中提供的脱敏反馈；
- AI不能把含义不同的反馈仅因关键词相同而强行合并；
- 每张候选问题卡片必须能够回到原始反馈；
- AI不能根据表达情绪自动决定优先级；
- AI生成的需求和验收条件只是草稿，必须由产品经理确认；
- AI不能修改或删除原始反馈；
- 模型不可用时，产品经理仍可手工分类并建立任务。

### 首版不做

- 不接入真实企业报销系统、客服系统和财务数据；
- 不保存真实姓名、手机号、发票、金额和单位信息；
- 不爬取网络评论或第三方平台数据；
- 不让AI自动决定开发优先级、发布时间和人员绩效；
- 不实现真实报销审批和资金支付。

### 核心验收场景

1. 导入多条“发票上传失败”的不同说法后，AI能生成候选问题并保留原文；
2. 同时包含“上传失败”和“看不到退回原因”的反馈可以拆成两个候选问题；
3. 含义不同但关键词相似的反馈不会在产品经理没有确认时直接成为候选问题；
4. 产品经理可以合并、修改或驳回AI候选结果；
5. AI生成需求草稿后，必须经过产品经理确认才能建立改进任务；
6. 开发或测试人员能够更新任务并记录验证结果；
7. 普通客服不能决定需求优先级或删除原始反馈；
8. 模型调用失败时，用户仍可手工完成分类和任务创建。

### 挑战点

看到一家科技公司的产品团队怎样把自然语言反馈变成可开发任务，并理解原始反馈、AI归纳、产品判断和正式需求之间的区别。

## 挑战赛道对比

| 选题 | 主要领域 | AI主要作用 | 主要边界 | 综合难度 |
| --- | --- | --- | --- | --- |
| 初中数学作业讲评 | 教育科技 | 生成讲评草稿和候选练习 | 教师审核、学生隐私、不自动定性 | 高 |
| 报销软件反馈与功能改进 | 软件产品研发 | 归类反馈、合并问题、生成需求草稿 | 原文回查、产品经理确认 | 高 |

# 第三部分：贯穿各章的阶段成果

## 第一章结束：选定行业和项目

学生提交一页“项目方向卡”：

| 内容 | 要求 |
| --- | --- |
| 选择方向 | 说明选择的赛道和题目 |
| 行业理解 | 用自己的话说明这个行业在完成什么工作 |
| 业务问题 | 说明当前流程可能出现的一个核心问题 |
| 主要岗位 | 列出可能使用系统的2至3类岗位 |
| 初步链路 | 画出业务从发起到结束的大致过程 |
| 已知与未知 | 区分已经知道、根据题目推测和后续需要确认的内容 |
| 选择原因 | 说明为什么愿意持续完成这个方向 |

第一章不要求设计字段、数据库表和接口。方向卡中的角色、问题和流程可以在第二章查阅行业资料后修改。

## 第二章结束：把项目需求说清楚

第二章结束时，学生只需要明确“要做什么、为谁做、做到什么程度”，不需要画页面、设计数据库和接口，也不需要写代码。

每组提交一份项目需求说明，内容包括：

1. **项目问题**：用一个具体场景说明现在谁在做什么、遇到了什么问题，以及系统准备帮助谁；
2. **使用岗位**：列出2至3类主要岗位，说明每类岗位要完成的事情；
3. **完整流程**：按顺序说明一件事由谁发起、谁处理、谁确认、怎样结束，并补充至少一种异常情况；
4. **关键规则**：说明哪些条件必须满足、哪些操作不允许、不同岗位分别能查看和处理什么；
5. **第一版范围**：分别列出必须完成的内容和明确不做的内容，保证范围足以走通一条完整业务流程；
6. **需求验收示例**：写出3至5个“在什么情况下，谁做什么，应该得到什么结果”的例子，至少包含正常、异常和无权限情况；
7. **依据和待确认项**：记录信息来自哪里，并把还没有确认的问题单独列出，不能把推测写成事实。

挑战赛道还要写清AI使用什么材料、生成什么内容、由谁确认，以及AI无法处理时怎样改由人工继续。本阶段只明确这些需求，不要求接入模型。

完成后，换一位同学阅读这份说明，应当能够回答：项目为什么做、谁来使用、事情怎样完成、必须遵守什么规则、第一版做到哪里、怎样判断需求已经满足。页面、数据和技术实现留到后续章节。
## 第三章结束：形成可实现设计

- 页面结构、岗位工作台和关键操作流程；
- 业务对象、数据库表和字段关系；
- 接口清单和主要输入输出；
- 页面、接口、Java对象和数据库字段对应关系；
- 正常、空数据、异常和无权限状态；
- 使用接近真实规模的虚构数据检查页面；
- 设计评审与修改记录。

## 第四章结束：完成核心功能编码

- 可启动的前端和后端工程；
- 数据库结构、初始化数据和演示账号；
- 至少一条核心业务链路的真实前后端实现；
- 关键状态流转、业务规则与权限控制；
- 对AI生成代码的阅读、修改和验证说明。

## 第五章及工具学习过程中：形成AI协作与版本记录

- 项目规则和必要业务上下文；
- 可执行的AI任务说明；
- 小范围修改、差异检查和验证记录；
- Git提交、分支和恢复记录；
- 一次AI错误理解业务规则或越界修改的复盘。

## 第六至八章结束：完成联调、Review和测试

- 接口联调记录；
- 页面、接口、数据库和业务状态能够互相对应；
- 业务、权限、错误处理和数据Review；
- 正常、异常、边界、并发和越权测试；
- 缺陷修复与回归结果。

## 第九至十章结束：完成部署、演示和交付

- 固定发布版本；
- 可复现的数据库初始化与虚构演示数据；
- 从新目录重新拉取并运行；
- 使用不同岗位账号完成核心业务演示；
- README、部署说明、已知限制和恢复方法；
- 项目复盘与最终答辩。

## 挑战赛道额外阶段成果

- AI输入、参考资料和输出结构说明；
- 人工审核、确认或降级路径；
- 由明确样例、模糊样例、冲突样例和依据不足样例组成的测试集；
- AI结果质量、限制和剩余风险说明；
- 模型不可用时仍可继续核心业务的方案。

# 第四部分：统一验收建议

## 评分维度

| 维度 | 建议权重 | 主要检查内容 |
| --- | ---: | --- |
| 行业与业务理解 | 10% | 是否理解岗位、单据、流程和行业边界，而非只替换名称 |
| 需求与范围 | 10% | 问题、角色、规则、MVP和不做项是否清楚 |
| 系统与体验设计 | 15% | 岗位工作台、页面流程、数据和接口是否一致 |
| 核心功能实现 | 25% | 前端、后端和数据库是否形成真实业务闭环 |
| 业务规则与权限 | 15% | 状态变化、角色权限、对象归属和异常处理是否有效 |
| AI协作与版本过程 | 10% | 是否说明AI做了什么、怎样检查、修改和恢复 |
| Review与测试 | 10% | 是否覆盖正常、异常、边界、并发和越权场景 |
| 部署与交付 | 5% | 是否能从新环境运行、演示并说明限制 |

挑战赛道仍按同一总分评价。AI功能的依据、人工确认、失败处理和评测结果计入核心实现、业务规则和测试，不因接入模型接口自动加分。

## 不建议作为完成度指标

- 页面数量；
- 数据表数量；
- 代码行数；
- 接口数量；
- AI生成内容的字数；
- 接入模型或工具的数量；
- 为了显得像“大平台”而增加的无关功能。

## 建议的最终演示结构

1. 用一分钟说明企业在完成什么业务、存在哪个问题；
2. 说明系统中的岗位、业务对象和核心规则；
3. 使用不同角色账号演示一条完整业务链路；
4. 展示一个正常场景、一个异常场景和一个越权场景；
5. 展示一次状态变化在页面、接口和数据库中的对应证据；
6. 说明一次AI参与开发的任务及验证过程；
7. 挑战赛道展示AI有依据回答、依据不足和模型失败三种情况；
8. 说明项目怎样部署、恢复和交给下一位维护者；
9. 说明未完成功能、已知限制和不能直接投入生产的原因。

## 选题组织建议

- 常规赛道作为默认选择，四个题目都能覆盖完整全栈学习链路；
- 挑战赛道适合能够稳定完成基础Web闭环，并愿意额外处理AI不确定性的学生；

- 不允许把电商、物流、养老、教育和研发功能混在同一个项目中；
- 第一章只选择行业和问题，第二章形成需求后允许有依据地调整项目范围；
- 行业从业者可以提供业务认识，但不承担项目验收和技术指导责任。
