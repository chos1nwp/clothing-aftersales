# 第七章 · Review 记录（业务规则 / 权限 / 错误处理 / 数据）

> Review 方式：先按四个维度自查清单逐项过一遍代码与页面，再把可疑点写成可执行的断言（第八章的 `scripts/acceptance-test.sh`），能用接口和数据库证伪的才算结论。
> 编号 D-01…D-11 按发现顺序，第八章测试报告在「缺陷修复与回归」里引用同一批编号。
> D-12、D-13 是写第五章过程记录时补登记的：当时按本文档的接口对照表逐个 `curl` 复核，才发现一处文档与代码不一致、以及一个此前没覆盖到的错误分类。过程本身记在 `docs/05-ai-collaboration.md` 第 7 节。
> D-14 是第九章「新目录重跑」时暴露的测试脚本缺陷：原目录跑绿不代表脚本自校验充分。

## 2. 缺陷明细与修复

### D-01 重复登记验货时报错原因误导（业务规则）

- **发现方式**：跑 happy-path 脚本时，对已验货的单据再次 `inspect`，返回「尚未登记收货，不能直接登记验货结果」，而事实是「已经验过货了」。
- **影响**：仓库人员会被引导去重新登记收货，掩盖真实的重复操作；测试取证也会对错因。
- **改法**：`AftersalesFlowService.inspect` 调整守卫顺序 —— 先看 `warehouse.isInspected()` 报「该售后单已完成验货登记」，再判状态，最后判是否已收货。
- **回归**：用例 D9/D10（未收货先验货 → 409 且提示「请先登记收到退回包裹」）、happy-path「重复提交验货结果 → [409] 该售后单已完成验货登记」。

### D-02 消费者看不到「撤销申请」（权限/前端）

- **发现方式**：浏览器实测详情页，待审核单据的消费者视角没有撤销入口；检查 `detail.html` 的 `secondaryPanel()` 拼接条件，角色三元判断写反。
- **影响**：需求「消费者在客服处理前可撤回申请」在页面上无法完成，接口其实是通的。
- **改法**：改为仅 `me.role === 'CONSUMER'` 时渲染撤销面板。
- **回归**：真实点击撤销，`AS202609300025` 状态变「已取消」、时间线补 `CANCEL`、可售后数量恢复；用例 C10–C12 固化。

### D-03 状态中文标签前后端漂移（业务规则/一致性）

- **发现方式**：对照 `AftersalesStatus` 与设计文档，前端把 `WAIT_FINAL_REVIEW` 显示为「待客服确认」。
- **影响**：同一状态在页面、接口、文档里出现三种说法，评审时容易被当成两个状态。
- **改法**：前端 `STATUS_LABEL` 统一为「待确认」，并把后端 `statusLabel` 作为首选来源。
- **回归**：用例 F4 断言接口返回的 `statusLabel` 含「待确认」。

### D-04 条件必填字段一直显示（错误处理/前端）

- **发现方式**：详情页验货面板选「合格」时「异常现象」输入框仍在页面上；计算样式发现 `display: block`。
- **影响**：作者样式表里的 `label { display: block }` 优先级高于浏览器默认的 `[hidden] { display: none }`，`el.hidden = true` 不生效，用户会对着隐藏不掉又非必填的字段困惑。
- **改法**：`styles.css` 显式声明 `[hidden] { display: none !important; }`，条件字段绑定 `change` 与 `input` 两个事件同步。
- **回归**：浏览器实测选「合格」后该字段 `getComputedStyle(...).display === 'none'`；行内必填错误提示正常。

### D-05 申请页可点、后端 409：前后端规则不同口径（业务规则）

- **发现方式**：浏览器实测对「白色/L 衬衫」点申请售后并填写说明，提交后被后端拦下「该商品已有正在处理中的售后申请」，但订单页当时显示「可售后 1 件」并且按钮可点。
- **影响**：用户走完整整一个表单才被拒绝，体验差；也说明页面的「可售后」语义（数量额度）与后端「同一商品同时只允许一个流程」是两条规则，页面只表达了前一条。
- **改法**：`OrderMapper.xml` 的占用统计子查询一并算出 `open_count`，`OrderItemView` 新增 `openAftersales`；订单页把按钮置灰并显示「已有处理中的售后，先处理完再申请」，申请页深链进来也给出同样说明。后端规则不变，仍是最终裁决方。
- **回归**：用例 C2/C3（重复申请仍 409）、C12（撤销后 `afterSaleableQuantity` 恢复且 `openAftersales=false`）。

### D-06 仓库工作台「全部」比子页签数据还少（业务规则/接口设计）

- **发现方式**：浏览器点「全部」页签只有 1 条，点「已交客服」却 2 条，子集大于全集显然不对。
- **根因**：`AftersalesQueryService.staffList` 里有条隐式规则 —— 仓库角色 + 不带 `status` 参数时，服务端擅自改成只查 `WAIT_RECEIPT`。前端「全部」页签不带状态，于是被悄悄过滤。
- **影响**：接口行为不诚实，调用方无法从参数推断结果；也造成 UI 数据比真实待办少。
- **改法**：删掉该隐式默认，`status` 为空就是不过滤，前端页签自己传明确状态。顺带去掉因此多余的 `LoginUser` 入参。
- **回归**：不带参数返回 11 条，是两个子页签（1 条 / 2 条）的超集；用例 F6 依赖批量带出的 `warehouseRecord`。

### D-07 改完页面刷新看不到变化（工程/体验）

- **根因与影响**：Spring Boot 默认给静态资源较长的缓存头，演示中反复出现「代码改了但页面还是旧的」，容易被误判成逻辑 bug。
- **改法**：`application.properties` 设 `spring.web.resources.cache.period=0` 与 `cachecontrol.no-cache=true`，让浏览器每次带 `ETag/Last-Modified` 回源校验。
- **回归**：响应头确认 `Cache-Control: no-cache`；改样式后刷新即生效。生产部署如需强缓存，在第九章部署说明里作为可调项写明。

### D-08 非法输入被判成服务端错误，且提示泄露异常类名（错误处理）

- **发现方式**：写验收脚本时一次取值失败，请求打到 `/api/aftersales/null`，返回 500 且 `message` 为「系统繁忙，请稍后重试：MethodArgumentTypeMismatchException」。
- **影响**：客户端把编号拼错属于 4xx，却被记为服务端故障并污染错误日志；把异常类名回给浏览器对排障没帮助，也没有信息泄露价值。
- **改法**：`GlobalExceptionHandler` 增加 `MethodArgumentTypeMismatchException`（→ 400「地址里的「id」不合法，请重新进入页面」）与 `HttpMessageNotReadableException`（→ 400「请求内容格式不正确，请刷新页面后重试」）两个处理器；兜底 500 的提示去掉异常类名，细节只留在日志里。
- **回归**：用例 G1–G5，其中 G5 断言返回给浏览器的两条提示都不含 `Exception` 字样。

### D-09 演示脚本把日志和取值混在同一条 stdout（测试脚本）

- **发现方式**：`happy-path-demo.sh` 里换货链路的后续请求全部报「Unexpected end of JSON input」。
- **根因**：`B_ID=$(... | node -e 'console.log(...)')` 取 id 时，说明文字也被命令替换一起捕获，变量里塞进了日志，拼出的 URL 是坏的。
- **改法**：id 只走 stdout，说明文字走 stderr（`console.error`），命令替换只拿到纯 id。
- **回归**：脚本重跑通过，验收脚本沿用同一约定。

### D-10 验收用例对演示数据的假设错了（测试脚本）

- **发现方式**：首轮 39 项失败里有 D1「客服要求补充材料」返回 409。
- **根因**：用例想验证「要求补充 → 消费者重新提交」，直接拿了演示数据里**已经处于** `NEED_SUPPLEMENT` 的 `id=2` 去调 `review`，而 `review` 只接受待审核单 —— 后端拒绝是对的，用例假设错。
- **改法**：改为新建一张单再走完整补充流程；同时把「撤销」用例改到演示数据里那张待补充单上（`NEED_SUPPLEMENT` 属于允许撤销的状态），既修正假设又顺带覆盖状态集合。
- **回归**：组 D 从 409 变 0，且 D5 断言时间线留下 `SUPPLEMENT_REQUEST` + `RESUBMIT` 两条往来。

### D-11 断言在错误的数组层级上取值（测试脚本）

- **发现方式**：第二轮运行只剩 1 项失败——C12「撤销后可售后数量恢复」返回 `missing`。
- **根因**：`/api/consumer/orders` 返回的是**订单数组**，商品在 `order.items` 里；helper 按顶层 `id=6` 匹配到的是订单 id=6，于是取不到商品字段。数据库里订单 id 与订单商品 id 恰好都是小整数，很容易看错层级。
- **改法**：先 `flatMap(o => o.items)` 再按商品 id 过滤；顺手删掉这个容易误用的通用 helper，改为就近写明确的一行式取值。
- **回归**：C12 通过；同时确认 `openAftersales=false` 与数量恢复是同一份数据（D-05 的口径）。
- **教训**：断言脚本里「按 id 找对象」必须先按「接口返回 → 代码 → 数据库行」三层各查一次，确认数组层级，否则失败会伪装成产品缺陷。

### D-12 不存在的接口地址被判成 500（错误处理）

- **发现方式**：写第五章时按 `docs/06-integration.md` 的接口对照表逐个探测，`GET /api/auth/current` 返回 **500**。先以为是接口缺失，查 `AuthController` 才发现真实端点是 `GET /api/auth/me`（`common.js:54` 用的就是它），文档那一行写错了 —— 见 D-13。但地址写错本身不该由服务端背锅，于是继续追这个 500。
- **根因**：D-08 补了两个 400 处理器，兜底的 `@ExceptionHandler(Exception.class)` 仍是 500。Spring Boot 3.2 对未匹配的路径抛 `NoResourceFoundException`，正好被兜底捕获，把「链接不存在」报成「系统繁忙」。
- **影响**：与 D-08 同类且更隐蔽——前端拼错路径、爬虫、旧书签都会污染服务端错误日志，排查方向被指向服务端故障；对调用方也没有区分「这个接口没有」和「这个接口挂了」的余地。
- **改法**：`GlobalExceptionHandler` 增加 `NoResourceFoundException` 处理器 → 404「这个地址不存在，请刷新页面后重试」，日志级别降为 `warn` 且只记资源路径，不打印堆栈。
- **回归**：用例 G6/G7（新增，断言 404 与提示措辞），G1–G5 仍通过，证明 400 与 500 的判定没有被这个处理器抢走。

### D-13 联调文档把接口名写错（文档与代码不一致）

- **发现方式**：同 D-12，按 `docs/06-integration.md` 的对照表调接口时 500。
- **根因**：文档写的是 `GET /api/auth/current`，代码里是 `GET /api/auth/me`。前端用的是正确的 `/api/auth/me`，所以六组页面实测全绿也没有暴露它——**只有人读的文档会错，机器跑的路径不会错**，这类错误不在任何测试覆盖范围内。
- **影响**：交付文档的接口对照表正是答辩时要给人照着走的，错一个名字就是一次当场翻车。
- **改法**：改为 `GET /api/auth/me`；并把「文档里出现的每个接口路径都用 `curl` 打一次」定为收尾动作（本次即按此核对，才连带发现 D-12）。
- **回归**：`/api/auth/me` 登录态下返回当前用户；错误路径的样本 `/api/auth/current` 保留在 G6 里，让这条文档失误留下可执行的痕迹。

### D-14 并发用例把「没读到响应」当成「409+0」通过（测试脚本）

- **发现方式**：第九章在新目录 `git clone` 后跑 `scripts/acceptance-test.sh`，首轮 **87 通过 / 1 失败**，失败项是 E4「失败的一方拿到可理解的冲突提示（响应里没有 其他客服）」。同一个脚本在原目录跑过十几轮都是绿的。
- **根因**：E1 的判定是 `SUM=$((E1C1 + E1C2))` 并要求等于 409，代表「一 0 一 409」。但 `code` 取值失败时返回**空串**，bash 算术把空串当 0 —— 于是「两个请求里有一个根本没读到结果」也能凑出 409 让 E1 假通过，紧接着 E4 去读那个空文件必然失败。**E4 的失败其实是在替 E1 报错**：断言里缺了「取证本身是否成立」这一层。
- **判定过程**：在同一个新目录实例上给脚本加临时诊断（打印两个响应文件的字节数与内容）后连跑两轮，都是 `cs01=37字节 code=0` / `cs02=103字节 409`、88 项全通过，不复现——说明不是并发规则变了，而是那一轮取证断了（Windows 下刚写完的文件被瞬时读到空是有的）。产品侧的结论仍然成立：E2「动作只记录一次」、E3「状态只前进一步」都通过，所以归为测试脚本缺陷而不是业务缺陷。
- **改法**：新增 E1a「两个并发响应都解析出了数字业务码」（用 node 校验两个取值都是 `^\d+$`），并把 E4 读取的文件从「临时算出来的字符串」改成提前算好的 `LOSERSLOT`。**判定条件变严了**：E1 现在必须先证明两份响应都读到了，才允许谈并发结论。没有放宽任何断言。
- **回归**：新目录实例连续三轮 89/0；原目录实例 89/0；`flow-demo.sh`、`happy-path-demo.sh` 同批通过。
- **教训**：跨进程取证的断言，要把「读到没有」和「读到的对不对」分成两条断言写；否则一次偶发的空响应会伪装成业务规则失效，反过来也可能把真的并发缺陷藏进算术里。

## 3. Review 中确认保留的设计决定

| 决定 | 理由 | 风险与说明 |
| --- | --- | --- |
| 不用 Spring Security，自写 `@RequireRole` + 拦截器 | 课程要求小型系统讲清权限口径即可，Session + 注解足够，配置成本低 | 只做演示级鉴权；生产应换成过滤器链与 CSRF 措施，已在第九章「已知限制」登记 |
| 乐观并发用 `where id=? and status=?`，不引入 `version` 字段 | 状态机本身是天然的版本条件，冲突语义清楚（409） | 若将来同一单据允许多字段并行修改，需要真正的行版本 |
| 退款金额为「单价 × 数量」的模拟值 | 题目不接真实资金，重点是规则可追溯 | 不处理优惠券分摊、运费、部分退款，属于明确的范围外 |
| 凭证图片本地磁盘存储 + UUID 重命名 | 单机可复现，避免外部依赖 | 多实例部署需换对象存储，写在第九章 |
| 演示数据日期相对 `NOW()` 生成 | 任何时间重新 clone 都能跑出「在售后期内」的样例 | 若把系统时间调到很久以前，期限用例的分布会变化 |
