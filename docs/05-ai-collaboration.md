# 第五章 · AI 协作与版本过程记录

> 本章记录的是**过程证据**：AI 具体做了什么、人怎样检查、发现过什么错、怎样修回来、留下哪些 Git 痕迹。
> 所有结论都能对应到一次提交、一段 diff、一条脚本断言或一次浏览器实测，不写"AI 提效明显"这类无法核对的话。

## 1. 分工与一轮协作的形状

| 谁 | 负责什么 |
| --- | --- |
| 人（开发者） | 定题与评分口径、划定范围（不做购物车/支付/真实资金，退款只做模拟金额）、给出每阶段的验收标准、逐阶段确认后再进下一阶段、数据库口令只在本地掌握 |
| AI 助手 | 需求整理与措辞、技术方案比较与选型建议、建表脚本与后端实现、前端页面与脚本、自测取证、文档起草 |

一轮协作固定四步，任何一步不过就不进下一步：

```
可执行的任务说明  →  小范围实现（尽量单文件、可回滚）  →  差异检查（git diff / git show）  →  验证（接口脚本 + 数据库对账 + 浏览器点击）  →  提交
```

"小范围"是可核对的：本轮最小的功能提交 `e2b3ced` 只动 1 个文件、15 增 1 删；`8949865` 里为对齐前后端规则所做的后端改动是 `OrderMapper.xml +6/-3`、`OrderItemView +3/-2`、控制器 `+2/-3`。

## 4. 复盘：一次 AI 对业务规则的误解

**AI 得到的原始要求**：仓库岗位登录后"看到自己该处理的售后单"（需求说明书里的岗位工作台描述）。

**AI 的实现（错误）**：把这条岗位约束写进了查询服务，让接口在"仓库角色 + 不带 `status` 参数"时自动按 `WAIT_RECEIPT` 过滤：

```java
String effectiveStatus = status;
if (user.role() == UserRole.WAREHOUSE && (status == null || status.isBlank())) {
    effectiveStatus = AftersalesStatus.WAIT_RECEIPT.name();   // 服务端擅自替调用方决定过滤条件
}
```

**误解链条在哪里**：岗位约束的正确落点是「页面默认展示哪个页签」+「接口按参数过滤」。AI 把它理解成「接口要有岗位默认值」，于是同一条规则被实现了两次，第二次还是隐式的。前端"全部"页签按"不传参数=不过滤"的常理去写，结果撞上这条默认规则。

**暴露方式**：浏览器实测。仓库工作台「全部」页签 1 条，而它的子集「已交客服」页签 2 条——子集大于全集，显然不可能。

**影响**：不只是 UI 少数据。接口行为不诚实，任何调用方都无法从参数推断返回；评审时也会被"岗位权限"和"过滤条件"两件事混在一起误导。

**修法**：删掉服务端这段隐式默认，`status` 为空就是不过滤，页签自己传明确状态；顺带去掉因此不再需要的 `LoginUser` 入参（`AftersalesQueryService.staffList`、`StaffAftersalesController.list`）。

**回归**：不带参数返回 11 条，是两个子页签（1 条 / 2 条）的超集；验收用例 F6 依赖并复用了这条批量返回。

**防复发**：写进设计口径——**服务端不代替调用方做默认过滤**；缺省语义只允许出现在页面层。同类问题在需求示例 4（"仓库不能提前收货"）上也提醒过：规则要在**动作入口**判定，而不是在**列表查询**里偷偷判定。

## 5. 复盘：一次越界改动（改配置时动了不相干的行）

**任务范围**：只允许给 `application.properties` 增加静态资源缓存相关的两行配置（原因见缺陷 D-07：改完页面刷新看不到效果）。

**AI 的越界行为**：编辑时把上下文里的 `app.max-evidence-count=6` 一并删掉了。这行是售后凭证数量上限的业务配置，与本次任务毫无关系。

**当时的补救（不彻底）**：发现缺失后手工把它补了回来，但补在了新增配置的下方，于是文件里出现**同名键两次**：

```
app.max-upload-size-bytes=5242880
app.max-evidence-count=6        ← 原有
# 演示项目改完页面要能立刻看到效果…
spring.web.resources.cache.period=0
spring.web.resources.cache.cachecontrol.no-cache=true
app.max-evidence-count=6        ← 补回来的重复行（已删除）
```

值相同，Spring 取后者，**运行行为没变**，所以两个演示脚本和页面实测都没报错——这正是这类改动最危险的地方：它不产生可观察故障，只留下腐化的配置。

**暴露方式**：写本章时按"差异检查"流程执行 `git show 8949865 -- src/main/resources/application.properties`，看到 `+5/-0` 里出现一个本该已存在的键。也就是说，**是在提交之后的复核中发现，而不是在提交前的 diff 检查中发现**——检查动作做了，但做在事后。

**修法**：删除重复行（`grep -c evidence-count` 由 2 变 1，`0/-1`），与 §7 的两个发现一起随 `f2648e8` 提交。

**防复发（已落成固定动作）**：

1. 改配置文件的提交，diff 必须出现删除行时**逐行问一句"这行属于本次任务吗"**；不属于就恢复原行，只保留新增。
2. 新增键前先 `grep` 同名键，禁止靠"我记得它在哪"来补行。
3. 把 `git show <commit> -- <file>` 纳入阶段收尾动作，而不是等下一章写文档时才做。

**另一个同类的"说明与内容不符"记录**：提交 `8e09fb9` 的说明写的是"增加正常收束链路演示脚本"，但它实际只有 8 增 4 删——脚本主体在上一个提交里已经加了，这次真正做的是修取证方式（id 走 stdout、日志走 stderr）。说明文字当时按"新脚本"口吻写，掩盖了这是一次缺陷修复。后续提交（`e2b3ced`）改为按"修了什么"来命名，并在测试报告里把这条取证缺陷登记为 D-09。

## 7. 复盘：按文档逐条复核接口，抓到两个测试覆盖不到的问题

前面几节的失误都在「跑代码」时暴露。这一节的两条不是——它们只有**照着文档手动走一遍**才会出现，所以值得单独记。

**动作**：写本章 §3 的版本记录时，顺手把 `docs/06-integration.md` 的「角色 → 页面 → 接口」对照表当成清单，对每一行 `curl` 一次，确认文档写的路径真的存在。

**发现 1（文档缺陷 D-13）**：表里写 `GET /api/auth/current`，代码里实际是 `GET /api/auth/me`（`common.js:54` 用的就是后者）。前端一直是对的，所以六个页面实测、88 项断言全都绿——**只有人读的文档会错，机器跑的路径不会错**，这类错误天然在测试覆盖之外。

**发现 2（产品缺陷 D-12）**：调那个不存在的地址返回的是 **HTTP 500**。原因正是 §5/§6 里那类「兜底吞掉细分错误」的写法：`GlobalExceptionHandler` 补了 400 处理器之后，剩下的 `Exception` 兜底仍返回 500，而 Spring Boot 对未匹配路径抛的 `NoResourceFoundException` 刚好落进兜底。于是「链接写错」被报成「系统繁忙」，还会在服务端日志里留一条完整堆栈。

**为什么原有 86 项断言没抓到**：G 组测的都是「接口存在但输入非法」（`/api/aftersales/abc`、坏 JSON），没有一条测「路径本身不存在」。断言矩阵是按需求场景写的，不是按 HTTP 错误码全集写的，所以「404 该长什么样」这件事从来没进过用例表——它属于测试报告第 8 节「未覆盖范围」那类问题，只是这次是靠读文档而不是靠跑脚本发现的。

**修法与回归**：`NoResourceFoundException` → 404，日志降为 `warn` 只记资源路径；文档改回 `/api/auth/me`。断言新增 G6/G7（**故意用 `/api/auth/current` 这个真实写错的地址当样本**，让这次文档失误在后端里留痕），总数 88；三个脚本同批重跑通过。提交 `f2648e8`。

**沉淀的检查动作**：交付前把文档里出现的每个接口路径、每个表名、每个字段名逐个对代码或数据库核一次。本章之后这条列入第九章的发布前清单。
